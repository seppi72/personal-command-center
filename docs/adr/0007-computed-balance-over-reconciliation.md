# Computed Balance over manual reconciliation

An Account's Balance could be modeled two ways: derived from its `openingBalance` plus every logged Transaction (always mathematically consistent with the log, but can drift from the owner's real-world bank balance if a Transaction is ever forgotten), or a value the owner periodically types in to match their actual bank/wallet balance (always accurate to reality, but can silently disagree with the Transaction log itself, and needs its own reconciliation UI).

We chose the computed form — `Balance = openingBalance + Σ(Transactions)` — matching the "derive, don't duplicate" shape Work Hours already uses over Time Entries (`docs/adr/0005-work-hours-rollup-transitive-fold.md`). This also keeps the expense/income charts, Category breakdowns, and Projected Balance (`CONTEXT.md`) all reading from the same single source of truth as the Balance figure itself, rather than two numbers that could quietly disagree. The trade-off is that a forgotten Transaction understates reality with no built-in correction; reconciliation (an owner-initiated Balance adjustment that itself logs a correcting Transaction) is a deliberate, separable follow-up if drift turns out to matter in practice, not part of this design.
