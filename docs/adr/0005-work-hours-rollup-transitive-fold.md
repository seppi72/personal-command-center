# A Work Hours rollup by Project/Client/Course folds in everything the container holds, not just direct Time Entries

Ticket #25 (Work Hours reporting) needs to answer "how many hours went into Project X" — but a Time Entry attaches to exactly one of {Task, Project, Client, Course} directly (ADR-0004), and most Project-shaped work is logged against a Task, not the Project itself. A rollup that only summed Time Entries whose `project_id` pointed straight at Project X would miss most of the real hours, silently under-reporting unless the owner also checked every Task total and added them by hand.

We chose transitive fold-up: a Project's total is its own direct-to-Project entries plus every entry logged against any Task belonging to that Project (Sprint-grouped or not — Sprint doesn't change which Project a Task's entries fold into). A Client's total is its own direct-to-Client entries plus each of its Projects' totals (which are themselves already folded). A Course's total is its own direct-to-Course entries plus every entry logged against any Task belonging to that Course. A Task has nothing below it in this hierarchy, so a Task's total is direct entries only — there's no fold to do.

The alternative — direct-only totals per container — was rejected because it's a materially wrong answer to the question the report exists to answer, not just an incomplete one. The trade-off: the rollup query is now a real join/aggregation across the container hierarchy (Task → Project → Client, Task → Course) instead of a flat `GROUP BY container_id`, and if the container hierarchy ever changes shape (e.g. Task gains a second Project-like container), this fold logic has to change with it.
