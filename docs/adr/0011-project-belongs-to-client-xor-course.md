# A Project may belong to a Client or a Course, never both

School work has the Project shape: a semester group assignment has sub-tasks, its own deadline, and its own logged hours, exactly like a freelance Project does. Until now a Project could only optionally belong to a Client, and a Task belonged to a Project *xor* a Course (ADR-0003), so the only ways to model coursework were to invent a second Course-scoped grouping concept alongside Sprint, or to flatten a multi-week assignment into a single Task.

We chose to give Project a second possible parent: a Project may belong to a Client, or to a Course, or to neither — never to both. Client-vs-Course on a Project is itself an exclusive choice, mirroring the exclusivity Task and Time Entry already use for their own containers: a Project is billable work for a Client or coursework for a Course, and the two are alternate parents of the same kind rather than orthogonal tags. Task's own rule is unchanged in spirit — a Task still has exactly one container — but is restated as "a Task belongs to a Project or directly to a Course," since a Project may now itself sit under a Course.

The alternative, a Course-scoped grouping modelled on Sprint, was rejected because it would rebuild deadlines, sub-tasks and time tracking under a new name for no gain beyond leaving ADR-0003 untouched. The trade-off is that this amends three existing decisions rather than one: ADR-0003 (Task's container xor), ADR-0004 (Time Entry's four-way container exclusivity, whose Project and Course arms can now be related rather than strictly peer), and ADR-0005 (Work Hours' transitive fold, which gains a Course → Project → Task path — a Course's total now folds in its Projects' totals as well as its own direct entries and its directly-owned Tasks' entries, exactly the way a Client's total already folds in its Projects). ADR-0005 anticipated this: it warned that if Task ever gained a second Project-like container the fold logic would have to change with it, and it now does.
