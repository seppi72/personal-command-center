# In-app notifications, not OS push, for v1

`CONTEXT.md`'s Notification entry has always had two aspects: membership in the "needs you" queue (the data) and delivery through a push/alert channel (the transport). The queue itself is new work regardless, but the transport had a real fork: an actual OS-level push notification (APNs, so the owner is alerted even when neither the Mac nor iOS app is open) versus in-app-only surfacing (the queue is fetched and shown inside PCCUI, with no delivery outside the running app).

No push infrastructure exists anywhere in this codebase today — every existing use of the word "push" is `CalendarSyncService` pushing Personal Commitments to CalDAV, unrelated to notifying the owner of anything. Real APNs push would need, from scratch: an Apple Push Notification service certificate/key (provisioned through Apple's developer portal — a human-only step, not something an agent can do from this environment), a device-token registration endpoint per client, and a delivery service that calls APNs and handles its response/retry semantics. That's a full new subsystem, not an incremental extension of an existing one — a much larger bet than standing up the queue itself.

We chose in-app-only for v1: the Notification queue is exposed over the API and surfaced inside PCCUI (a `NotificationsView` listing open, undismissed rows), the same way every other domain in this codebase surfaces its data — no APNs, no device tokens, no background delivery service. The trade-off is that a Notification only reaches the owner when they open the app and look, not the moment it's created; that's acceptable because nothing about this domain requires the wake-the-owner-immediately guarantee push exists for; the queue being visible on next open is enough.

Real push remains a clean, separable follow-up: it adds a delivery mechanism on top of the same stored queue, rather than requiring the queue itself to be reshaped. Revisit if there's an actual case for alerting the owner while neither app is open.
